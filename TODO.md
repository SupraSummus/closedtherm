- Only the setpoints are throttled; every reading (pressure, return temperature, modulation, fault) still costs an OpenTherm exchange on every pass. Give the slow readings their own interval the way `pushSetpoints()` has one.
- A setpoint write that fails is not retried until the next refresh, and `/` reports the requested value either way, so a rejected setpoint looks applied.
- Stale OpenTherm data: `/` reports the last values even when the boiler stopped answering; decide what to publish after N failed exchanges, then test it.
- `savePreference()` ignores what `Preferences` returns, so a write that saves nothing — a key over the 15 character cap, a full partition — passes silently and the setting reverts at the next reboot. Check the result and say so on serial, and in `/` if there is somewhere sensible to put it. (This cap is why the PI settings are named `pi_*`: the name is the key, so it has to fit in 15 characters. Only `temp_sensor_tau`, which sits exactly on the cap, is held there by a `static_assert`; every other key is a bare string literal that nothing measures.)
- The median in `thermometer.h` is aimed at supply dips under radio bursts, which is a hypothesis, not a measurement. Report the raw reading and `thermometer.median` on `/` next to the filtered value for a while to see what each stage actually rejects; `WiFi.setSleep(false)` is the one-line experiment that would steady the current draw if that is the cause. (`temp_sensor_tau=0` already gives the median alone on `/`, which is half of this without a code change, but only by switching the low-pass off rather than alongside it.)
- The median window is 16 `loop()` passes, so how long a dip it can reject is however long 16 passes take, and nobody has timed a pass. Time one, and if the loop ever slows down or speeds up much, give the window a length in seconds instead.
- Nothing checks the room sensor, and nothing says what the controller does when the reading cannot be trusted. A disconnected one reads near 0 mV, which `thermometer.h` turns into a few hundred degrees; the PI source answers that by clearing the CH demand, so the house goes cold with `/` reporting `ch_demand` false as if that were a decision. Reject readings outside a sane band, say so in the JSON, and pick what the source does then — hold the last demand, fall back to `manual`, or lean on the boiler's own frost protection. The integral's floor makes recovery part of that question: a reading of a few hundred degrees pins the integral at `outMax` and NVS keeps it there, so a sensor that comes back finds a controller asking for 80 °C until it has wound down.
- `handleSet()` still names the sketch's own five settings three times over — validation branch, apply block, NVS key. `piSettings` in `pi_source.h` shows the shape that collapses it, and it is closer to paying than it was: the five are two bools and three floats, and the three floats (`requested_ch_temp`, `requested_dhw_temp`, `temp_sensor_tau`) are a name and a band each, which is a `PISetting` row with the member pointing outside one struct. Two tables and two lookups is still about what it saves at this size, so the sixth setting is probably the one to do it on, or a float table alone with the two bools left as they are.
